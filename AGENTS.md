# it-smi — цифровая визитка (тестовое задание)

Greenfield-проект: кода ещё нет, единственный источник требований — `TZ.md`.
Прочитай его целиком перед планированием: там же пример GraphQL-запроса, который обязан работать как есть.

## Жёсткие требования (не «оптимизировать»)

- Стек зафиксирован заказчиком и оценивается поштучно: TypeScript, Node.js, NestJS, Prisma, GraphQL, Docker.
  Не заменять на REST/TypeORM/Express/`graphql-yoga` — каждая из перечисленных технологий должна реально использоваться.
- GraphQL Playground = Apollo Sandbox (штатный `@nestjs/apollo` driver), а не сторонний UI.
- При запуске приложение само готовит и наполняет БД: миграции + seed внутри entrypoint контейнера,
  без ручных шагов. «Корректная работа после запуска с нуля» — отдельный критерий оценки.
- `README.md` — часть сдачи, а не украшение: обоснование архитектурных решений обязательно.
- Сдаётся двумя ссылками: развёрнутый бэкенд и git-репозиторий.

## Что реально оценивают

- Не объём кода, а решения: разделение слоёв (resolver → service → data-доступ), читаемость, поддерживаемость.
- Вложенные GraphQL-поля должны решаться батчингом (DataLoader / `include`-запросы), а не N+1.
  Это названо в ТЗ отдельным пунктом — типичная точка, где теряются баллы.
- На собеседовании решение будут менять вживую: предпочитай простое и очевидное «умному».

## Домен (из `TZ.md`)

`profile` (имя, краткое описание, ссылки) со вложенными `skills`, `experience` (компания, должность,
период, достижения), `projects` (название, ссылка). Структуру БД и API выбираем сами — но она должна
покрывать пример запроса из ТЗ без доработок.

## Источники истины

- `TZ.md` — исходные требования заказчика, не редактировать.
- `tz-detail.md` — детализация (архитектура, модель данных, GraphQL-схема, Docker, DoD).
- `todo-global.yml` — сквозной план по группам `и`, `а`, `д`, `б`, `в`, `г`, `е`, `ж`, `з`.
  Порядок обязателен: инфраструктура (`д`) идёт до данных (`б`), миграции требуют живой PostgreSQL.
  Тесты и проверки (`е`) заблокированы до готовности инфраструктуры и шаблонов модулей.
- `data/profile.yml` — контент визитки; `prisma/seed/main.ts` только читает его, данные в коде не хардкодить.
- `config/` — конфигурация проекта: только YAML, без кода. `api-fields.yml` (контракт API:
  `queries` — запросы верхнего уровня, `properties` — скаляры, `references` — связи с указанием
  сущности и колонки-идентификатора),
  `seed.config.yml` (пути и стратегии записи сидинга), `environment.schema.yml` и
  `profile-data.schema.yml` (JSON Schema переменных окружения и контента).

## Язык

- Русский: `README.md`, документация, комментарии в `.md`-файлах, коммиты.
- Английский — **только код**: идентификаторы, имена полей GraphQL и Prisma, комментарии, JSDoc.
- Это осознанное отступление от глобального правила «вся документация на английском».

## Конвенции репозитория

- Git и npm инициализированы; `type: commonjs` в `package.json` не менять на `module` — ESM ломает Nest CLI и Prisma.
- `config/` в корне — только конфиги в YAML; код, который их читает и проверяет, лежит в `src/`, `prisma/`
  или `scripts/` по назначению. Новый конфиг добавляется в `config/`, а не в `src/`.
- Сущности описаны одним типом `{ id, type }` (`src/common/contracts/types.ts`), где `type` — имя
  делегата Prisma-клиента (`profile`, `socialLink`, …). Полей сущностей сервер не знает и DTO не
  заводит: строка БД уходит в GraphQL как есть. Связи (включая колонку `profileId`) описаны в
  `config/api-fields.yml` → `references`, поэтому в коде нет ни имён таблиц связей, ни колонок.
  Объявления запросов и полей-связей не пишутся руками: их выпускает `prisma/generators/graphql/graphql.generator.mts`
  в `src/generated/graphql/resolvers/` из `schema.prisma` и контракта, а поведение (404, проверка страницы,
  батчинг) живёт в `src/graphql/queries/entity-queries.ts` и `src/graphql/loaders/entity.loader.ts`.
  Если правилу действительно нужна колонка — его тип объявляется рядом с этим правилом.
- `.history/` — локальные бэкапы редактора, не исходники. Не читать как код; уже в `.gitignore`.
- Персональных данных профиля в репозитории нет: в `data/profile.yml` лежит демонстрационный
  контент на `example.com`, который проходит валидацию по `config/profile-data.schema.yml`.
  Реальные данные ставит автор; выдуманные компании, должности и достижения не добавлять.
- Ожидаемая точка входа для проверки: `docker compose up --build` поднимает всё с нуля,
  GraphQL доступен на `/graphql` (+ Sandbox). `README.md` сейчас в репозитории отсутствует: он
  пишется заново ближе к сдаче (релизный пункт документации), поэтому изменение запуска фиксируй
  в самом коде и конфигах (`docker-compose.yml`, `Dockerfile`, `package.json`, `config/`), а не
  в README.
- Каждый текстовый файл заканчивается ровно одним переводом строки (`\n`): ни пустой строки после,
  ни отсутствующего перевода. Источник истины — правило `@stylistic/eol-last` в `eslint.config.mjs`,
  `npm run lint` обязан быть зелёным. Формат соблюдает тот, кто пишет файл; в глобальных правилах
  агентов (`agent-behavior.md`) это требование уже записано.
