# Развёртывание стенда на Dockhost

## 1. Что это и когда читать

Демонстрационный стенд проекта `it-smi` на платформе Dockhost: **один образ** (NestJS отдаёт и
GraphQL API, и собранную страницу Angular), рядом PostgreSQL на сетевом томе. Обновление стенда —
`git push` в ветку `deploy`: платформа собирает образ и перезапускает контейнер.

Читайте этот файл, когда нужно: развернуть стенд с нуля (или восстановить после удаления ресурсов),
поднять его после пересоздания проекта, обновить версию, откатить неудачную сборку или разобрать
ошибку деплоя.

### Адрес стенда

| Что | Значение |
| --- | --- |
| Домен стенда | `https://u6fu-w4sl-fj2p.gw-1a.dockhost.net` (динамический домен платформы) |
| Страница ручной проверки | `/` |
| GraphQL (Apollo Sandbox в браузере) | `/graphql` |
| Healthcheck | `/health` → `{"status":"ok"}` |
| Проект платформы | `my-project`, кластер `ru-1a` |
| Ветка деплоя | `deploy` в `https://gitverse.ru/gpb/test-task-it-smi.git` |

Домен динамический: при пересоздании ресурсов он может измениться, и адрес выше устареет.
Фактический хост всегда берётся командой `dockhost network domain list`.

### Состав ресурсов

| Ресурс | Имя | Параметры | Чем создаётся |
| --- | --- | --- | --- |
| Проект | `my-project` | кластер `ru-1a` | вручную (шаг 1) |
| Репозиторий (пайплайн) | `app` | `Dockerfile`, контекст `.`, память сборки 1024 MiB | `dockhost.yaml:43-51` |
| Контейнер | `app` | образ из пайплайна `app`, порт 3000/TCP, переменные `DATABASE_URL`, `NODE_ENV`, `PORT` | пайплайн `app` + `container update` (шаг 6) |
| Контейнер | `postgres` | `postgres:17.11-alpine`, порт 5432/TCP, память 256 MiB | `dockhost.yaml:60-79`, `compose apply` |
| Том | `db-data` | ssd, 1 GiB, смонтирован в `/var/lib/postgresql/data` | `dockhost.yaml:54-58`, `compose apply` |
| Домен | `main` | динамический адрес платформы, HTTPS | `dockhost.yaml:83-84`, `compose apply` |
| Маршрут | `web` | `/` → `app:3000` (единственный маршрут) | `dockhost.yaml:95-100`, `compose apply` |

Второго контейнера и второго маршрута нет: статику клиента отдаёт тот же процесс Nest
(`useStaticAssets`, каталог `public` рядом с `dist` — `src/main.ts:33`), поэтому `/`, `/graphql`
и `/health` обслуживает один порт 3000.

Секретов в `dockhost.yaml` нет: пароль базы и строка подключения — переменные проекта, в файле
только ссылки `$ИМЯ`.

## 2. Предпосылки

1. **CLI `dockhost` установлен и авторизован** (проверено на версии 0.23.1). Проверка:
   `dockhost project list` отвечает списком проектов, а не ошибкой авторизации.
2. **Доступ к репозиторию** `https://gitverse.ru/gpb/test-task-it-smi.git` с правами на push:
   `git ls-remote origin deploy` возвращает хеш, `git push` проходит.
3. **Платформа собирает только ветку `deploy`** — это зафиксировано в `dockhost.yaml:46`
   (`repositories.app.branch`). Рабочая ветка (та, что открыта: `git branch --show-current`) стенд
   не обновляет: её нужно выложить в `deploy` отдельной командой (шаг 3).
4. **Репозиторий публичный**, поэтому `repositories` в `dockhost.yaml` не содержат логина: платформа
   клонирует его по HTTPS анонимно. При переводе репозитория в приватный в `dockhost.yaml` нужно
   добавить `username`/`password`.
5. **Файл `dockhost.yaml` в корне репозитория — источник описания проекта.** Он закоммичен, и
   `dockhost compose apply` создаёт по нему том, базу, домен и маршрут. Править состояние проекта
   в панели «поверх» файла не нужно: при следующем `apply` расхождения исчезнут.

Если `dockhost container list` пуст, а тома нет в `dockhost volume list` — стенд удалён или ещё не
разворачивался. Тогда проект восстанавливается по шагам ниже: домен и репозиторий обычно остаются,
том и `postgres` создаёт `compose apply`, контейнер `app` появляется после сборки образа.

## 3. Развёртывание с нуля по шагам

**Порядок принципиален.** Контейнер `app` создаёт не секция `containers` файла, а пайплайн из блока
`repositories` (`dockhost.yaml:21-24`): пока не прошла первая сборка, контейнера `app` не существует
и `dockhost compose apply` падает с `unknown container app`. Поэтому сначала создаётся проект и
задаются переменные, затем выкладывается ветка и собирается образ, и только после этого применяется
`dockhost.yaml`. Шаг «применить файл» до первой сборки — известная ловушка; повторный `apply` после
сборки проходит без ошибок.

Каждый шаг ниже содержит цель, команду и ожидаемый результат. Если результат не совпал — не
переходите к следующему шагу, посмотрите раздел «Типовые ошибки».

### Шаг 1. Проект `my-project` в кластере `ru-1a`

**Цель.** Убедиться, что проект платформы существует (или создать его). Имя проекта в панели должно
совпадать с полем `project` в `dockhost.yaml:33`: `compose apply` ищет проект по этому имени.

Проверка:

```bash
dockhost project list
```

**Ожидаемый результат.** В списке есть `my-project` на кластере `ru-1a`, и последующие команды
работают без указания проекта.

Если проекта нет — создайте его в панели Dockhost: «Новый проект», имя `my-project`, кластер `ru-1a`
(кластер выбирается при создании). CLI-вариант:

```bash
dockhost project create --name my-project
```

После создания повторите `dockhost project list`.

### Шаг 2. Переменные проекта

**Цель.** Задать четыре переменные, которые читают `postgres` и `app`. Значения секретов в
репозиторий и в этот файл не попадают — только имена.

| Переменная | Секрет | Значение | Где задаётся |
| --- | --- | --- | --- |
| `POSTGRES_USER` | нет | `it_smi` | `dockhost.yaml:36-39`, применяется `compose apply` |
| `POSTGRES_DB` | нет | `it_smi` | `dockhost.yaml:36-39`, применяется `compose apply` |
| `POSTGRES_PASSWORD` | **да** | пароль базы | панель или `dockhost environment variable set` |
| `DATABASE_URL` | **да** | строка подключения Prisma | панель или `dockhost environment variable set` |

`POSTGRES_USER` и `POSTGRES_DB` объявлены прямо в `dockhost.yaml` (не секреты), поэтому вручную их не
набирают: они появляются после `compose apply` (шаг 5). Секреты задаются до первой сборки —
контейнер `app` читает `DATABASE_URL` на старте, и без неё падает с
`Environment variable not found: DATABASE_URL`.

Строка подключения строится с **хостом `postgres`** (имя контейнера базы внутри сети проекта), а не
`localhost`: у контейнера базы нет внешнего порта, приложение и Prisma ходят к `postgres:5432`.
Шаблон (угловые скобки заменяются фактическим паролем):

```
postgresql://it_smi:<пароль>@postgres:5432/it_smi?schema=public
```

Задать секреты можно в панели проекта (раздел переменных) либо CLI — команда принимает только флаги
и требует `--name`:

```bash
dockhost environment variable set --name POSTGRES_PASSWORD --value '<string:32>'
dockhost environment variable set --name DATABASE_URL \
  --value 'postgresql://it_smi:<пароль>@postgres:5432/it_smi?schema=public'
```

`--value '<string:32>'` — шаблон генерации значения, который понимает CLI: вместо литерала
подставляется сгенерированная 32-символьная строка. Тот же пароль нужен в строке подключения
`DATABASE_URL`, поэтому проще передать литерал пароля обеими командами (или сгенерировать его один
раз и подставить в оба значения).

Проверки: имя и значение передаются только флагами (`--name`/`--value`), позиционные аргументы
команда не принимает; после установки результат виден в `dockhost environment variable list`.

**Ожидаемый результат.** `dockhost environment variable list` показывает `DATABASE_URL`,
`POSTGRES_DB`, `POSTGRES_PASSWORD`, `POSTGRES_USER`. Значения секретов не попадают в репозиторий, в
этот файл и в переписку.

### Шаг 3. Выложить ветку в `deploy`

**Цель.** Отдать платформе актуальное дерево. Собирается только ветка `deploy`, поэтому рабочую
ветку нужно в неё выложить.

```bash
git status --porcelain                  # ожидаемо: пусто, дерево закоммичено
git ls-remote origin deploy             # текущий хеш ветки deploy на GitVerse
git push origin HEAD:deploy             # выложить текущий коммит в deploy
```

**Ожидаемый результат.** Вывод `git push` содержит обновление `deploy`; повторный
`git ls-remote origin deploy` совпадает с локальным `git rev-parse HEAD`. В панели репозитория `app`
появляется новая сборка (автоматически, до двух минут) либо её запускают вручную на следующем шаге.

### Шаг 4. Первая сборка образа `app`

**Цель.** Собрать образ и тем самым создать контейнер `app`. Без этого шага `compose apply`
не сможет связать сервис `app` с контейнером и упадёт с `unknown container app`.

```bash
dockhost repository build app
```

Сборка идёт в одном образе: `npm ci`, генерация, `nest build` и `ng build` клиента. Если сборка
падает по памяти — см. раздел «Типовые ошибки» (OOM).

**Ожидаемый результат.** Сборка завершается успешно; в `dockhost container list` появляется
контейнер `app` (образ из последнего пайплайна), в `dockhost repository list` у репозитория `app`
видна ветка `deploy` и успешная сборка.

### Шаг 5. Применить `dockhost.yaml`

**Цель.** Создать по файлу том `db-data`, контейнер `postgres`, домен `main` и маршрут `web`. Файл
идемпотентен: существующие ресурсы он обновляет, отсутствующие создаёт.

```bash
dockhost compose apply
```

Путь и флаги необязательны: `-f/--file` по умолчанию указывает на `dockhost.yaml` в текущем
каталоге.

**Ожидаемый результат.** Команда проходит без ошибок; `dockhost volume list` показывает `db-data`,
`dockhost container list` — `postgres` и `app`, `dockhost network domain list` — домен `main`.

Если контейнера `app` ещё нет (шаг 4 не выполнен), команда завершится ошибкой `unknown container app`
и создаст только том и `postgres`. Это не поломка: выполните шаг 4, затем повторите `compose apply`.

### Шаг 6. Переменные и порт контейнера `app`

**Цель.** Задать контейнеру `app` рантайм-переменные и порт. Это единственное, чего нет в
`dockhost.yaml`: контейнер `app` создаёт пайплайн, а его переменные живут в панели. До этого шага
`app` может перезапускаться с `Environment variable not found` — это ожидаемо и лечится здесь.

**`dockhost container update` заменяет список переменных и портов целиком, а не дополняет его.**
Поэтому набор передаётся всегда полностью — и при первой настройке, и при любом последующем
изменении (память, образ). Имя контейнера передаётся флагом `--name`, а не позиционно, и команда
ожидает образ:

```
Usage: dockhost container update --name <name> --image <image> [options]
```

```bash
dockhost container update --name app \
  --image <образ> \
  --variable 'DATABASE_URL:$DATABASE_URL' \
  --variable 'NODE_ENV:production' \
  --variable 'PORT:3000' \
  --port 3000/TCP
```

`--variable` принимает пару `имя:значение` и повторяется для каждой переменной: список переменных
заменяется целиком. `<образ>` берётся из `dockhost container list` — после первой сборки (шаг 4) это
образ из последнего успешного пайплайна `app`.

`$DATABASE_URL` в одинарных кавычках — ссылка на переменную проекта, её подставляет платформа, а не
локальный shell. `NODE_ENV=production` не выключает Sandbox: интроспекция и Sandbox включены в
приложении явно. `PORT=3000` совпадает с портом сервиса `app` и маршрутом (шаг 7).

**Ожидаемый результат.** В `dockhost container list` (или в панели) у контейнера `app` три
переменные — `DATABASE_URL`, `NODE_ENV`, `PORT` — и порт 3000/TCP. Контейнер перезапускается;
`dockhost container logs app --tail 50` показывает старт без `Environment variable not found`.

### Шаг 7. Домен и маршрут

**Цель.** Убедиться, что домен и единственный маршрут на месте, и узнать фактический адрес стенда.
Домен `main`, сервис `app` и маршрут `/` → `app:3000` описаны в `dockhost.yaml:81-100`, поэтому
обычно их создаёт `compose apply` (шаг 5) — отдельных команд не нужно.

```bash
dockhost network domain list
dockhost network route list
```

**Ожидаемый результат.** Домен `main` в статусе `ready` с HTTPS; его хост (вида
`u6fu-w4sl-fj2p.gw-1a.dockhost.net`) записан как адрес стенда, переход на `https://<хост>/` открывает
страницу клиента (окончательная проверка — раздел 4). Маршрут один: `/` → `app:3000`; список
маршрутов подтверждается командой `dockhost network route list`. Если домена нет — повторите
`dockhost compose apply`.

### Шаг 8. Проверка после развёртывания

**Цель.** Убедиться, что стенд отвечает целиком. Порядок проверок и ожидаемые ответы — раздел 4.

## 4. Проверка после развёртывания

Проверки идут от дешёвых к содержательным. `<хост>` — фактический домен из шага 7.

1. **Живость процесса.**

   ```bash
   curl -sS https://<хост>/health
   ```

   **Ожидаемо:** `{"status":"ok"}`
   (`src/features/health/health.controller.ts:15`). Любой другой ответ, 502 или таймаут означают, что
   контейнер `app` не поднялся — смотрите логи (пункт 4).

2. **Страница клиента.**

   ```bash
   curl -sSI https://<хост>/
   ```

   **Ожидаемо:** `200` и `content-type: text/html`. В браузере `/` показывает страницу ручной
   проверки API; неизвестный путь отдаёт 404 — это нормально, у клиента нет маршрутизатора.

3. **GraphQL Sandbox.** Открыть `https://<хост>/graphql` в браузере.

   **Ожидаемо:** загружается Apollo Sandbox (интроспекция включена явно). `curl` того же адреса без
   `Accept: text/html` отдаёт JSON-ответ GraphQL — это не ошибка.

4. **Логи старта: миграции, сидинг, запуск.**

   ```bash
   dockhost container logs app --tail 50
   ```

   **Ожидаемо:** по порядку `==> prisma migrate deploy`, затем
   `==> seed (dist/prisma/seed/main.js)`, затем `Application is running` и строка о прослушивании
   порта. Ошибок Prisma, `P1001` (база недоступна) и `Environment variable not found` нет.
   Шаги выполняет `docker/entrypoint.sh:9-22` — ручных команд на стенде нет.

5. **Запрос из ТЗ через Sandbox.** Вставить в Sandbox запрос (источник — `TZ/TZ.md:36-51`):

   ```graphql
   query {
     profile {
       name
       description
       skills {
         name
       }
       experience {
         company
         position
       }
       projects {
         name
       }
     }
   }
   ```

   **Ожидаемо:** `200`, массив `errors` отсутствует, `name` и `description` заполнены, коллекции
   `skills`, `experience` и `projects` непустые (по данным `data/profile.yml`).

6. **Границы пагинации (быстрая проверка валидации).**

   ```graphql
   query {
     profiles(limit: 101) {
       id
     }
   }
   ```

   **Ожидаемо:** ошибка `BAD_REQUEST` с понятным сообщением о предельном значении `limit`.

Если проверки 1–4 проходят, а 5 нет — стенд жив, проблема в данных или схеме: смотрите пункт 4
(сидинг) и `config/api-fields.yml` (видимость полей).

## 5. Обновление и откат

### Обновление

```bash
# 1. Выложить текущую ветку в deploy (собирается только она).
git push origin HEAD:deploy

# 2. Платформа замечает изменения до двух минут и сама собирает образ и обновляет контейнер.
#    Ручной запуск сборки, если ждать не хочется:
dockhost repository build app

# 3. Перезапуск без пересборки — например, после смены переменных контейнера или проекта:
dockhost container restart app
```

После любого из вариантов повторите проверки из раздела 4 (минимум `/health` и логи).

Помните: если меняли переменные контейнера `app`, передавайте **полный** набор (шаг 6) — иначе
список заменится частичным и `DATABASE_URL` пропадёт.

### Откат

Два способа, оба возвращают предыдущее состояние кода:

- **Через панель:** раздел «Сборки» репозитория `app` → выбрать предыдущий успешный пайплайн →
  перезапустить его. Образ и контейнер возвращаются к тому коммиту.
- **Через git:** выложить предыдущий коммит в `deploy` с перезаписью истории:

  ```bash
  git push --force origin <хеш-предыдущего-коммита>:deploy
  ```

  Затем дождаться автоматической сборки или запустить `dockhost repository build app`.

Миграции откат не отменяют: `prisma migrate deploy` применяет только вперёд, и схема остаётся на
версии нового коммита. Если откат затрагивает схему данных, базу нужно приводить в согласие
отдельно.

## 6. Типовые ошибки

- **`Invalid params` при создании контейнера** — имя контейнера короче трёх символов (например
  `db`). Поэтому база называется `postgres`; переименование потребует правки `DATABASE_URL`
  (хост в строке подключения — имя контейнера).
- **`Environment variable not found: DATABASE_URL` в логах `app`** — переменные контейнера потеряны.
  Причина почти всегда одна: `dockhost container update` вызван с частичным набором и **заменил**
  список. Повторите шаг 6 с полным набором: `dockhost container update --name app --image <образ>
  --variable 'DATABASE_URL:$DATABASE_URL' --variable 'NODE_ENV:production' --variable 'PORT:3000'
  --port 3000/TCP`.
- **`unknown container app` при `compose apply`** — контейнера `app` ещё нет: его создаёт пайплайн
  из блока `repositories` только после первой сборки. Сначала `dockhost repository build app`,
  затем повторите `dockhost compose apply`.
- **OOM при сборке** (`npm ci`, `nest build`, `ng build` идут в одном образе) — память сборки задаётся
  в `dockhost.yaml` полем `repositories.app.memory` (`dockhost.yaml:51`, сейчас `1024MiB`): у
  `dockhost repository update` опции `--memory` нет. Поднимите значение в файле, выполните
  `dockhost compose apply`, затем повторите `dockhost repository build app`.
- **404 на статике после пересборки** — проверьте, что сборка клиента кладёт файлы в
  `client/dist/browser`, а runtime-стадия `Dockerfile` копирует их в `./public`: каталог `public`
  должен лежать рядом с `dist` (`src/main.ts:33`). Если страница отдаёт 404, а `/health` — 200,
  проблема именно в этой раскладке.
- **`compose dump --override` затирает `dockhost.yaml`** — команда перезаписывает файл текущим
  состоянием проекта и теряет комментарии и ещё не применённые секции. Перед запуском сделайте
  копию файла; обычная работа ведётся правкой `dockhost.yaml` + `compose apply`.
- **Репозиторий недоступен платформе** — репозиторий публичный и читается по HTTPS без логина. При
  переводе в приватный добавьте `username`/`password` в `dockhost.yaml` (`repositories.app`).
- **`/graphql` или `/` отдают 404, хотя домен `ready`** — контейнера `app` нет либо маршрут не
  создан: проверьте `dockhost container list` и `dockhost volume list`, затем пройдите шаги 4–6.
  Пустой список контейнеров при живом домене — ровно этот случай: ресурсы удалены, стенд
  восстанавливается по `dockhost.yaml`.
- **Смена пароля базы** — пароль живёт в переменных проекта `POSTGRES_PASSWORD`/`DATABASE_URL` и
  внутри самой базы. После смены значения в панели пароль нужно сменить и в PostgreSQL
  (`ALTER USER`), затем перезапустить `app`, иначе подключение не установится.

## 7. Ограничения стенда

- **Одна реплика `app`.** Миграции и сидинг выполняются при старте контейнера: две реплики устроят
  гонку миграций. Горизонтальное масштабирование потребует вынести миграции из `entrypoint`.
- **Миграции и сидинг на старте.** `docker/entrypoint.sh`: `prisma migrate deploy` → сидинг
  (идемпотентный, повторный запуск обновляет те же строки) → `exec node dist/main.js`. Ручных шагов
  на стенде нет, но и отдельного job миграций тоже нет.
- **Диск 1 GiB без бэкапов.** Без тома `db-data` база теряется при перезапуске контейнера; снапшоты
  и бэкапы не настроены.
- **Один образ на всё.** Правка клиента пересобирает и backend: сборка дольше, зато версия страницы
  и API всегда совпадают.
- **Нет gzip и долгого кэша статики.** Файлы отдаёт Express (`useStaticAssets`), без сжатия и
  `immutable`-кэша: `main-*.js` уходит ~370 КБ как есть, `cache-control: public, max-age=0`.
- **Нет SPA-fallback.** У клиента нет маршрутизатора, страница одна: неизвестный путь отдаёт 404,
  и это ожидаемо.
- **Память сборки резервируется и тарифицируется.** 1024 MiB нужны только на время сборки; рантайм
  работает на 512 MiB (`app`, фактическое потребление ~216 MiB).
- **Секреты только в переменных.** Пароль базы и `DATABASE_URL` живут в переменных проекта; в
  репозитории и в этом файле — только имена.

## 8. Открытые решения

- Собственный домен и сертификаты вместо динамического адреса платформы.
- CI-прогон тестов перед выкладкой.
- Снапшоты и бэкапы базы.
- Сжатие и кэш статики (`compression`, `Cache-Control: immutable`).
- Перенос миграций из `entrypoint` в отдельный job при необходимости масштабирования.
