# Цифровая визитка: backend на NestJS, Prisma, GraphQL и Docker

## Вступление

Проект выполнен в соответствии с подходом **spec-driven development** ([Martin Fowler](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)):

- сначала задача фиксируется, как спецификация, с критериями готовности, затем ИИ реализует её по этой спецификации.
- составляется todo-лист процесса выполнения задачи
- Реализация построена как **мультиагентный процесс** в [opencode](https://opencode.ai): [агенты](https://opencode.ai/docs/agents/) с ролями планировщика, разработчика, тестировщика и ревьюера. 

- Спецификации и чеклисты хранятся в [Markdown](https://commonmark.org) и [YAML](https://yaml.org) рядом с кодом в [Git](https://git-scm.com),
- каждый результат проходит автотесты и код-ревью.

Главная инженерная цель: снизить скорость роста сложности по мере развития проекта. Для этого подсистемы сделаны слабосвязанными, а знание о данных и API не дублируется по коду: у него единственный источник истины, из которого выводится всё остальное. 

Поэтому с ростом функциональности стоимость изменений растёт плавно, а не лавинообразно.

Из этого вытекают приоритеты, на которые стоит смотреть в коде:

- **Расширяемость:** новая функциональность добавляется рядом с существующей, без переписывания готового.
- **Тестируемость:** независимые модули проверяются по отдельности, без поднятия всей системы.
- **Заменяемость:** детали реализации (хранилище, внешний сервис, библиотека) можно поменять, не затрагивая остальной код.
- **Читаемость и предсказуемость:** границы модулей и их ответственность понятны, а изменения в одном месте не приводят к сюрпризам в другом.
- **Согласованность:** данные и контракты API нигде не расходятся, потому что выводятся из одного описания.
- **Лёгкий вход в проект:** новому разработчику достаточно понять один модуль, а не держать в голове всю систему.

## Подсистемы

Одиннадцать подсистем backend. Для каждой — назначение, ключевые файлы и не больше трёх пунктов
«что важно знать».

| Подсистема | Назначение | Ключевые файлы |
|---|---|---|
| Конфигурация | YAML в `config/` и проверка окружения | `config/`, `packages/yaml-loader` |
| Модель данных | Таблицы, ключи, индексы, миграции | `prisma/` |
| Сидинг | Контент из `data/profile.yml` в базу | `data/`, `prisma/seed/` |
| Контракт API | Что публично и в каком порядке | `config/api-fields.yml` |
| Генерация | Артефакты из схемы и контракта | `prisma/generators/` |
| Доступ к данным | Чтение строк через порт | `src/db/`, `src/common/contracts/` |
| GraphQL-слой | Запросы, связи, батчинг, Sandbox | `src/graphql/`, `src/generated/` |
| Health | Проверка живости двумя входами | `src/features/health/` |
| Сборка и Docker | Образ, entrypoint, запуск | `Dockerfile`, `docker/` |
| Клиент проверки | Angular-страница проверки | `client/` |
| Качество | Тесты, линт, границы, инварианты | `eslint.config.mjs`, `tests/` |

### 1. Конфигурация

- Один читатель на все файлы — `packages/yaml-loader`: разбор, поиск корня и текст ошибки живут в
  одном месте, поэтому `config/api-fields.yml` не может разбираться двумя способами.
- Путь считается от корня проекта (первый каталог с `package.json`), а не от рабочего каталога:
  запуск из репозитория и из `/app` в контейнере работает одинаково. Цена — каждый вызов обязан
  передать `searchFrom`.
- В `config/` пять YAML, из них три — артефакты генерации: `api-fields.schema.yml`,
  `profile-data.schema.yml` и `dictionaries.yml`. Окружение проверяется до подключения к базе:
  обязательна `DATABASE_URL`, `PORT` в диапазоне 1–65535 (по умолчанию 3000), `NODE_ENV` из трёх
  значений.

Файлы: `config/*.yml`, `src/common/config/`, `packages/yaml-loader/src/`.

### 2. Модель данных

- `prisma/schema.prisma` — единственный источник структуры: семь моделей (`Profile`, `SocialLink`,
  `Skill`, `ProfileSkill`, `ProfileSocialLink`, `Experience`, `Project`) и один enum `SocialKind`.
- У каждой модели колонка `type String @default("<делегат>")` — дискриминант строки. В коде строка
  любой таблицы описана как `{ id, type }`, поэтому DTO на модель не заводится: строка уходит в
  GraphQL как есть.
- `Skill` и `SocialLink` — справочники: одна строка на навык (`name @unique`) и одна на ссылку
  (`url @unique`), а принадлежность профилю хранят таблицы связи `ProfileSkill` и
  `ProfileSocialLink` (`@@unique([profileId, skillId])`, `@@unique([profileId, socialLinkId])`).
  `onDelete: Cascade` на обеих сторонах связи делает каскад единственным путём удаления потомков.

Файлы: `prisma/schema.prisma`, `prisma/migrations/`, `src/common/contracts/`.

### 3. Сидинг

- Контейнер сам наполняет базу из `data/profile.yml`: проверка формы по JSON Schema, доменные
  правила (`experience-periods.check.ts`), запись одной транзакцией.
- Обновлений нет: таблицы очищаются, файл вставляется заново, поэтому повторный запуск даёт тот же
  состав, а не дубли. Провал на любой модели откатывает всё.
- Справочники пишутся в две фазы: строка справочника один раз на значение ключа (`Skill.name`,
  `SocialLink.url`), затем строка связи `ProfileSkill` / `ProfileSocialLink` с полученным `id`.
  Резолв идёт по значению из файла; повтор ключа в пределах профиля и значение без строки
  справочника — ошибка с путём `profile.skills[i]` или `profile.links[i]`.

Файлы: `data/profile.yml`, `config/dictionaries.yml`, `prisma/seed/`.

### 4. Контракт API

- `config/api-fields.yml` отвечает на вопрос «что публично»: `queries` — запросы верхнего уровня,
  `properties` — скалярные поля с описаниями, `references` — связи: колонка-идентификатор или
  таблица связи (`through`), `order` — порядок коллекций.
- Инверсия по умолчанию: чего нет в файле, того нет в API. Генератор помечает прочие поля
  `@HideField()`, поэтому новая колонка не появляется у клиента без решения о ней.
- Проверка выполняется дважды: на сборке (`npm run validate:api-fields`) и на старте в
  `src/main.ts` — конфиг копируется в образ отдельно от кода, и битый файл должен ронять запуск.

Порядок задаётся блоком `order`, а не колонкой в таблице:

```yaml
order:
  - category: { sort: asc, nulls: last }
  - name: asc
  - id: asc
```

Файлы: `config/api-fields.yml`, `src/common/config/api-fields.ts`, `scripts/api-fields.cli.ts`.

### 5. Генерация

- Два источника — `prisma/schema.prisma` и `config/api-fields.yml` — вместе с конфигами
  генераторов дают пять артефактов: классы GraphQL-типов, JSON Schema контракта, объявления
  резолверов, JSON Schema контента, объявления справочников (`config/dictionaries.yml`).
- Артефакты лежат в git: изменение видно в ревью, приложение не зависит от запуска генератора в
  образе. Актуальность держит тест паритета, который перегенерирует копию и сравнивает байт в байт.
- В артефактах только объявления; правила (404, пагинация, батчинг) живут в обычном коде, поэтому
  их можно прочитать и протестировать.

Сгенерированный резолвер — объявление без поведения:

```ts
@Query(() => Profile, { description: 'The business-card profile.' })
profile(): Promise<IEntity> {
  return this.findOne('profile');
}
```

Файлы: `prisma/generators/`, `prisma/scripts/`, `src/generated/`, `config/`.

### 6. Доступ к данным

- Между слоями стоит порт `IEntityQueryPort` с единственным методом `find`; провайдер регистрируется
  по токену `ENTITY_QUERY_PORT`. Слой `graphql` не импортирует `src/db`, и это проверяет линтер.
- Одна реализация `EntityRepository` на все таблицы: делегат выбирается по имени типа, аргументы
  `where`, `orderBy`, `take`, `skip` строит `argsOf`. Сервиса и маппера нет — 404 решает транспорт.
- Три формы чтения: страница, коллекция по родителям, список идентификаторов. Порядок берётся из
  контракта, запасной — `ID_ORDER` по `id` (защита от неизвестной таблицы, а не правило домена).

Файлы: `src/db/entity.repository.ts`, `src/db/find-args.ts`, `src/common/contracts/`.

### 7. GraphQL-слой

- Объявления резолверов генерируются, поведение написано: `EntityQueries` даёт 404 на пустой таблице
  и проверку страницы (`limit` 1–100, `offset` от нуля, по умолчанию 10 и 0).
- Вложенные поля читаются пакетом: три `DataLoader` в области запроса, ключ кэша — таблица,
  колонка и `id`, один `find` на пару «сущность и колонка» за тик. Коллекция через таблицу связи
  стоит двух чтений — строки связи и строки справочника. Число чтений зависит от набора таблиц, а
  не от числа строк: профиль с четырьмя коллекциями — семь чтений.
- Схема строится в памяти (`autoSchemaFile: true`), поэтому приложению не нужно писать в образ;
  интроспекция включена, `GET /graphql` отдаёт Apollo Sandbox, штатная страница Nest выключена.

Файлы: `src/graphql/`, `src/generated/graphql/resolvers/`, `src/schema.gql`.

### 8. Health

- Два входа: HTTP `GET /health` для `HEALTHCHECK` и мониторинга, GraphQL `health { status }` для
  клиента, который уже говорит с `/graphql`. Контейнеру нужен код ответа, клиенту — знакомое поле.
- Тип статуса один (`UHealthStatus = 'ok'`), поэтому два ответа не расходятся. Ни один вход не
  обращается к базе: иначе недоступность базы перезапускала бы живое приложение.
- Резолвер зарегистрирован в `HealthModule`, а не в `SCHEMA_RESOLVERS`: `graphql` не имеет права
  импортировать feature-модуль, поэтому регистрация остаётся там, где объявлен резолвер.

Файлы: `src/features/health/`, `Dockerfile`.

### 9. Сборка и Docker

- Три стадии образа: `deps` ставит зависимости по lock-файлу, `build` выполняет `npm run build`,
  `runtime` ставит production-зависимости и копирует `dist`, `config`, `data` и entrypoint.
- `docker/entrypoint.sh` работает с `set -e`: `prisma migrate deploy`, затем
  `node dist/prisma/seed/main.js`, затем `exec node dist/main.js`. Порядок задаёт entrypoint,
  поэтому приложение видит готовую базу.
- Процесс работает от пользователя `node`, `init: true` отдаёт сигналы через `tini`, `HEALTHCHECK`
  каждые 10 секунд вызывает `/health`. Prisma CLI лежит в `dependencies`: контейнер сам применяет
  миграции.

Файлы: `Dockerfile`, `docker/entrypoint.sh`, `docker-compose.yml`, `src/main.ts`.

### 10. Клиент проверки

- Angular-приложение в `client/` — инструмент проверки, а не витрина: отправляет произвольный
  документ, показывает JSON ответа, ошибки GraphQL и сети отдельно, длительность запроса.
- Обращается к своему адресу, а dev-сервер проксирует `/graphql` и `/health` на сервер, поэтому CORS
  не нужен. Цена — клиент запускается только через dev-сервер, статикой без прокси не работает.
- Кэш выключен (`fetchPolicy: 'network-only'`), ошибки возвращаются полями результата, поэтому
  страница не может застрять в загрузке. Ответ показывается как есть, без копии контракта.

Файлы: `client/src/app/`, `client/proxy.conf.json`, `client/proxy.conf.docker.json`.

### 11. Качество

- Пять проектов `npm run typecheck` плюс `tsconfig.seed.json`: сидинг компилируется отдельно и
  проверяется сборкой. Правило выбрано механическим: что можно посчитать, проверяет машина.
- Границы слоёв описаны в `eslint.config.mjs` правилом `boundaries/dependencies`: запрещены
  `db → graphql`, `graphql → db` и `common → оба`. Нарушение падает на проверке, а не позже.
- Структурные инварианты в `tests/unit/structure/` проверяют размер комментария, категорию файла,
  размещение типов и запрет `type` с объектным литералом. E2E идёт на живой PostgreSQL и требует
  Docker.

Файлы: `eslint.config.mjs`, `knip.jsonc`, `tests/`, `tsconfig*.json`.

## Как части работают вместе

Три сквозных сценария: холодный запуск, один GraphQL-запрос и изменение схемы. Принципы здесь не
повторяются — они разобраны в разделе [Подсистемы](#подсистемы); здесь важен порядок шагов и то, что
ломается при пропуске.

### 1. Запуск: `docker compose up --build`

1. Сборка образов: серверный из корня (три стадии) и клиентский из `client/`.
2. `npm run build`: `build:lib` → `prisma:generate` → `validate:api-fields` → `nest build` →
   `build:seed`; битый контракт останавливает сборку до запуска контейнера.
3. Ожидание базы: compose ждёт healthcheck `pg_isready`, `app` объявляет `depends_on` с условием
   `service_healthy` и раньше базы не стартует.
4. Миграции: entrypoint выполняет `prisma migrate deploy` — применяет закоммиченные
   `20261107094000_init` и `20261112120000_dictionary_m2m`, команда идемпотентна.
5. Сидинг: `node dist/prisma/seed/main.js` проверяет контент и пишет его одной транзакцией.
6. Контракт: `src/main.ts` повторяет `validateApiFields` — конфиг копируется в образ отдельно
   от кода, поэтому проверка нужна и здесь.
7. Окружение: `AppConfigModule` валидирует переменные до подключения к базе; без `DATABASE_URL`
   процесс завершается с кодом 1 и понятным сообщением.
8. Приложение: `PrismaService` открывает соединение, `GraphQLModule` строит схему в памяти.
9. Порт: сервер слушает `PORT` (по умолчанию 3000) и логирует адрес.
10. Готовность: `HEALTHCHECK` каждые 10 секунд вызывает `GET /health`; клиент проверки доступен
    на 5173 и ходит на сервер через прокси.

Что ломается: `set -e` в entrypoint останавливает цепочку на первом провале, поэтому битый контент
или неприменённая миграция не доходят до `node`, а приложение никогда не видит пустую схему.

### 2. Запрос: `POST /graphql`

1. HTTP: тело `{ query, variables }` с `Content-Type: application/json`; без заголовка Apollo
   отвечает 400 — это защита от подделки запросов, а не сбой.
2. Apollo: разбирает документ, проверяет его против схемы в памяти и отклоняет неизвестное поле
   до выполнения.
3. Резолвер: для поля `profile` вызывается сгенерированный `ProfileQueriesResolver.profile`,
   который наследует `EntityQueries` и передаёт ему имя сущности.
4. `EntityQueries`: `findOne` читает первую строку первой страницы или бросает
   `NotFoundException`; `findPage` проверяет окно через `assertPagination`.
5. Порт: резолвер внедряет `ENTITY_QUERY_PORT` и вызывает `find('profile', …)` — класс реализации
   он не видит, поэтому слои остаются независимыми.
6. Репозиторий: `argsOf` превращает порядок из контракта в `orderBy`, окно — в `take` и `skip`;
   `findMany` делегата — одно обращение к базе.
7. Строка: из базы приходит `IEntity` с фактическими колонками, наружу уходит как есть — маппера
   и DTO нет.
8. Вложенные поля: `ProfileRelationsResolver.links` вызывает `loader.load(row, 'links')`;
   загрузчик берёт из контракта `{ entity, property }` или `{ entity, through }` и кладёт запрос в
   `DataLoader`.
9. Пакет: `DataLoader` собирает обращения одного тика, группирует по паре «сущность и колонка» или
   по таблице связи и делает один `find` на группу; коллекция через таблицу связи — два чтения на
   группу, строки связи и строки справочника. Ключ кэша живёт в пределах запроса.
10. Ответ: `data` или `errors` при HTTP 200; `NotFoundException` несёт `extensions.status`, клиент
    обязан смотреть в `errors`, а не только на код ответа.

Проверка масштаба: профиль с четырьмя коллекциями стоит семь чтений — страница, по одному на
коллекцию с колонкой родителя и по два на коллекцию через таблицу связи — и при одном профиле, и
при трёх.

Что ломается: без пакетной загрузки каждое вложенное поле даёт запрос на строку — N+1, и число
обращений к базе растёт вместе с размером коллекции.

### 3. Изменение: схема, контракт, контент

1. Схема: правка `prisma/schema.prisma` — модель, колонка, индекс или связь. Новой модели нужны
   колонка `type` со значением по умолчанию и `onDelete: Cascade` на связи с профилем.
2. Миграция: `npm run prisma:migrate:dev` создаёт SQL в `prisma/migrations/` и применяет его; файл
   коммитится вместе со схемой.
3. Генерация: `npm run prisma:generate` обновляет пять артефактов и выполняет пост-обработку.
4. Контракт: `config/api-fields.yml` — запись в `properties`, `references` или `order`; новая
   модель получает блок `models.<Model>`.
5. Проверка: `npm run validate:api-fields` ловит опечатку в имени модели, поля, сущности или
   колонки и называет путь внутри файла.
6. Паритет: `npm test` перегенерирует артефакты в одноразовой копии и сравнивает с закоммиченными
   байт в байт.
7. SDL: `npm run schema:update` перезаписывает `src/schema.gql`; единственный писатель файла — тест.
8. Контент: `data/profile.yml` дополняется значениями; справочник дополнительно объявляется блоком
   `dictionaries.<Model>` в `prisma/generators/seed-schema/seed-schema.config.mts` — ключ строки,
   поле файла и таблица связи; генератор выпускает `config/dictionaries.yml`, руками файл в
   `config/` не правится.
9. Прогон: `npm run build:seed && npm run prisma:seed` локально или перезапуск контейнера — форма
   контента проверяется при сидинге.

Что ломается: пропущенная миграция даёт падение на первом чтении, пропущенная генерация — падение
теста паритета, пропущенный контракт — колонка в базе без поля в API.

### Что общего у трёх сценариев

- Порядок задан снаружи приложения: entrypoint готовит базу, контракт решает видимость, тест держит
  артефакты — код только исполняет.
- Ни один шаг не проверяется «на глаз»: провал виден на сборке, старте или тесте, а не в ответе.
- Все три сценария проходят через одни и те же источники истины, поэтому обход любого из них
  расходится с кодом, а не с документацией.

## Типовые доработки

Шесть типовых доработок. Формат один: что сделать по шагам и один подводный камень. Принципы
(инверсия контракта, генерация, порт) разобраны в разделе [Подсистемы](#подсистемы) и здесь не
повторяются.

### 1. Новое скалярное поле

Когда: значение хранится в той же строке, что и остальные поля модели.

1. `prisma/schema.prisma` — колонка; обязательная получает `@default`, необязательная — `String?`.
2. `npm run prisma:migrate:dev` — миграция в `prisma/migrations/`, файл коммитится.
3. `npm run prisma:generate` — обновляет пять артефактов и пост-обработку.
4. `config/api-fields.yml` — запись в `properties` с непустым описанием; при сортировке — в `order`.
5. `npm run validate:api-fields` — проверка контракта против новой схемы.
6. `data/profile.yml` — значение, если колонка обязательна.
7. `npm run schema:update` — состав полей GraphQL изменился.

Подводный камень: колонка в `order` без индекса читает таблицу целиком — индекс строится под
первые ключи порядка.

### 2. Новая сущность

Когда: у значения больше одного поля и строк может быть несколько — нужна своя таблица.

1. `prisma/schema.prisma` — модель с `id`, `type` со значением по умолчанию, полями и связью
   `Profile` с `onDelete: Cascade`; в `Profile` — обратное поле-коллекция.
2. Ключи: дочерней сущности — `profileId` и индекс под первые ключи порядка; справочнику — `@unique`
   по ключу (`name`, `url`) и индекс под порядок чтения, а принадлежность профилю — отдельная
   модель `Profile<X>` с `profileId`, колонкой цели, `@@unique([profileId, <цель>])`,
   `@@index([profileId])` и `onDelete: Cascade` в обе стороны.
3. `npm run prisma:migrate:dev`, затем коммит миграции.
4. `config/api-fields.yml` — блок `models.<Model>`: `description`, `properties`, `references`
   (для справочника — `through` с таблицей связи и её колонками), `order`.
5. `prisma/generators/seed-schema/seed-schema.config.mts` — для справочника блок
   `dictionaries.<Model>`: `key`, `property` (имя поля в `data/profile.yml`), `link` с моделью
   связи и колонками родителя и цели; неизвестная модель или колонка — ошибка генерации.
6. `npm run prisma:generate` — GraphQL-тип, блок в схеме контракта, определение в схеме контента,
   для справочника — ещё запись в `config/dictionaries.yml`.
7. `data/profile.yml` — коллекция под `property` справочника или под обратным полем; `npm run
   schema:update`.

Подводный камень: без `property` коллекция не появится в схеме контента под именем поля файла, а
имя таблицы связи из DMMF (`ProfileSkill`) в `data/profile.yml` не годится — строки связи движок
выводит из вложенности, и в файле их нет.

### 3. Новый запрос или связь

Когда: нужен ещё один вход в существующую таблицу или ещё одно поле-связь.

Новый запрос верхнего уровня:

1. `config/api-fields.yml` — запись в `queries`: имя, `description`, `entity`, `kind`
   (`one` или `page`).
2. `npm run validate:api-fields`, затем `npm run prisma:generate`.
3. `npm run schema:update`.

Новая связь:

1. Связь должна существовать в `prisma/schema.prisma`; иначе это сценарий новой сущности.
2. `config/api-fields.yml` — запись в `references`: `entity` и `property` для колонки-идентификатора
   либо `entity` и `through` с таблицей связи и её колонками.
3. `npm run validate:api-fields`, затем `npm run prisma:generate` — объявления полей-связей
   выпускаются в `src/generated/graphql/resolvers/`; `npm run schema:update`.

Загрузчик менять не нужно: он читает связь из контракта. Свой резолвер нужен только для поведения,
которого нет у форм `one` и `page` (фильтр, агрегат, объединение таблиц).

Подводный камень: правила стоимости запроса в проекте нет — ограничение только размер страницы
(1–100) и число чтений от батчинга.

### 4. Мутации и запись

Когда: контент должен меняться без правки `data/profile.yml` и перезапуска контейнера.

1. Порт записи — отдельный интерфейс и токен в `src/common/contracts/`, реализация в `src/db/`:
   `prisma.*` вызывается только там.
2. Резолвер `Mutation` объявляется вручную: генератор выпускает только запросы и поля-связи.
3. Входные типы: расширить `emitBlocks` в конфиге генератора или объявить рядом с резолвером.
4. Проверка входа: минимум — `BadRequestException` в резолвере, как в `assertPagination`.
5. Транзакция через `prisma.$transaction` для изменений в нескольких таблицах.
6. Права до мутаций: без аутентификации запись открыта любому клиенту.
7. `npm run schema:update` — SDL изменился.

Подводный камень: сидинг очищает таблицы и вставляет `data/profile.yml` заново при каждом старте,
поэтому строки, созданные мутацией, исчезают при перезапуске контейнера.

### 5. Несколько профилей и доступ

Когда: сервис обслуживает нескольких людей или организаций, и визитка перестаёт быть публичной.

1. Модель уже допускает несколько профилей (`slug` уникален, у `Experience` и `Project` есть
   `profileId`, навыки и ссылки связаны таблицами `ProfileSkill` и `ProfileSocialLink`); нужна
   колонка владельца и, если нужны учётные записи, таблица пользователей.
2. Сидинг пересматривается: сейчас он читает один корневой объект.
3. Аутентификация: guard, проверка токена, источник секрета.
4. Авторизация: правило «кто что видит» и его проверка на каждом входе.
5. Одиночный запрос получает аргумент (`slug` или владелец) — это ручной резолвер, а не запись
   в `queries`.
6. Чтение по колонке добавляется в порт, если фильтр не выражается текущими формами.
7. Тесты на отказ: чужой профиль не читается, анонимный запрос отклоняется.

Подводный камень: проверка прав в `@ResolveField` выполняется на каждую строку и превращает
пакетное чтение в N+1 — ограничение доступа должно попадать в `where` на уровне порта.

### 6. Эксплуатация

Когда: сервис выходит за пределы локального запуска или появляются требования к языкам и файлам.

1. Кэш чтения — на уровне порта или отдельным слоем перед ним, с ключом из таблицы, колонки и
   идентификаторов; при появлении прав — ещё и области доступа.
2. Наблюдаемость: метрики числа и длительности запросов, отношение «чтений на запрос», журнал
   ошибок с путём поля.
3. Развёртывание: убрать публикацию порта базы, вынести миграции в отдельный шаг, оставить
   `HEALTHCHECK`.
4. Локализация: поля-переводы в моделях или таблица переводов плюс понятие «язык запроса».
5. Файлы: внешнее хранилище, колонка со ссылкой, ограничение размера и типа, проверка владельца.

Подводный камень: кэш перед загрузчиком ломает пакетность — каждый резолвер снова начнёт
обращаться к данным по строке.

## Команды

Сборка и проверки:

- `npm run build` — библиотека, генерация, проверка контракта, `nest build`, компиляция сидинга;
- `npm run lint` и `npm run lint:fix` — стиль, форматирование и границы слоёв;
- `npm run typecheck` — пять проектов TypeScript;
- `npm test` — юнит-тесты, включая паритет артефактов и SDL;
- `npm run test:e2e` — e2e на живой PostgreSQL, требует Docker;
- `npm run knip` — неиспользуемые файлы, экспорты и зависимости.

Работа со схемой и данными:

- `npm run prisma:migrate:dev` — создать и применить миграцию локально;
- `npm run prisma:generate` — генерация артефактов и пост-обработка;
- `npm run validate:api-fields` — контракт против сгенерированной схемы;
- `npm run schema:update` — перезаписать `src/schema.gql`;
- `npm run build:seed && npm run prisma:seed` — собрать и прогнать сидинг.

Запуск:

- `docker compose up --build` — база, миграции, сидинг, приложение, клиент;
- `curl -fsS http://localhost:3000/health` — проверка живости;
- `http://localhost:3000/graphql` — Apollo Sandbox и сам эндпоинт.
