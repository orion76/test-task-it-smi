# Цифровая визитка: backend на NestJS, Prisma, GraphQL и Docker

## Вступление

Это тестовое задание, выполненное в тесном сотрудничестве с ИИ: не как автодополнение кода, а как
инженерный процесс с ролями, артефактами и приёмкой. Средой работы был opencode, где отдельные
агенты `planner`, `coder`, `tester` и `reviewer` отвечали за планирование, код, тесты и ревью.

Каждая задача — папка в `.opencode/tasks/` с `_task.md` (требования и критерии готовности) и
`_todo.yml` (чеклист с идентификаторами пунктов). Статусы вёл только планировщик, а отчёты ходили
файлами `.opencode/messages/<роль>-<инициатор>.yml`, чтобы длинный текст не терялся в чате.

Инженерная цель была одна: чтобы каждая следующая доработка стоила дешевле предыдущей. Для этого
снижалась связанность подсистем, а знание о данных и API не дублировалось по коду — у него ровно
одно место, из которого остальное выводится.

Единственный источник истины о структуре — `prisma/schema.prisma`; о публичном API —
`config/api-fields.yml`. Всё, что из них следует (типы GraphQL, декларации резолверов, JSON Schema
контента), выпускается генераторами, а не копируется руками.

Генерация выбрана сознательно: ручная копия расходится с источником молча. Слои, которые ничего
не добавляют (отдельный `service`, маппер записей в DTO), не заводились: пустой переход стоил бы
поддержки, но не защищал бы инвариант.

Ошибки конфигурации обнаруживаются на старте, а не в первом запросе: переменные окружения,
контракт API и файл контента проверяются до подключения к базе. Каждое спорное решение закрыто
тестом — числом SQL-запросов, правилом стоимости операции, сверкой артефактов с генерацией.

Результат — один GraphQL-эндпоинт `/graphql` с Apollo Sandbox: профиль с навыками, опытом,
проектами и ссылками. Миграции и сидинг выполняет entrypoint контейнера, поэтому
`docker compose up --build` на чистой машине поднимает приложение с уже наполненной базой.

## Конфигурация и валидация

Вся внешняя конфигурация лежит в `config/` как YAML, а её форма описана JSON Schema: переменные
окружения — `config/environment.schema.yml`, контракт API — `config/api-fields.yml`, структура
контента — `config/profile-data.schema.yml`. Альтернатива, конфигурация в TypeScript-объектах,
потребовала бы сборки ради смены значения и держала бы проверку отдельно от данных. Читает файлы
одна библиотека `packages/yaml-loader` (`loadConfig`), поэтому разбор и ошибки у всех одинаковы.

`loadConfig` не угадывает корень проекта: вызывающий передаёт `searchFrom` (`__dirname` или
`import.meta.dirname`), а библиотека идёт вверх до каталога с `package.json`
(`packages/yaml-loader/src/project-root.ts:63`). Поэтому путь `config/api-fields.yml` означает одно и
то же для `npm run`, `node dist/main.js` и генератора, которого Prisma запускает сама.

AJV-опции не спрятаны в библиотеке, их передаёт вызывающий. Окружению нужны `coerceTypes` и
`useDefaults`: из `process.env` всё приходит строкой, а `PORT` объявлен целым
(`src/common/config/constants.ts:18`). Файлу контента те же опции навредили бы —
молчаливое `"1"` → `1` скрыло бы ошибку автора вместо сообщения с путём до поля.

Проверка окружения идёт через `ConfigModule.forRoot({ validate })` до подключения к базе
(`src/common/config/app-config.module.ts:16`): без `DATABASE_URL` приложение не стартует и говорит об
этом прямо, а не падает позже на `connection refused` из недр Prisma.

Альтернатива — читать пути от `process.cwd()`, как делают обычно. Она ломается при запуске из
другого каталога и в контейнере; цена явного `searchFrom` — каждый вызов обязан его передать,
иначе библиотека падает с подсказкой, что именно передать.

## Модель данных и Prisma

Домен описан пятью моделями и одним enum в `prisma/schema.prisma`: профиль, ссылки, навыки, места
работы и проекты. Схема — единственное место, где объявлены колонки, и единственный вход для
миграций: в `prisma/migrations/` лежит одна закоммиченная миграция `init`, её контейнер применяет
при старте. Пара `finished`/`endedAt` — завершённость места работы: `true` и дата против `false` и
пустой даты; пару проверяет сидинг (`prisma/seed/data/experience-periods.check.ts:45`).

Идемпотентность сидинга держится на натуральных ключах: `slug` уникален у профиля, пара `profileId`
+ `name` уникальна у навыка (`prisma/schema.prisma:119`). Суррогатный ключ потребовал бы хранить
идентификаторы в файле контента и сверять их вручную; натуральный ключ позволяет повторной записи
обновить ту же строку, а исчезнувшую из файла — удалить.

Порядок вывода задан колонкой `order`, которую сидинг проставляет по индексу элемента в массиве.
Без неё порядок `findMany` не гарантирован, и страницы «плавали» бы между запросами. У `Profile`
такой колонки нет: корень один, и он упорядочен по `createdAt` (`src/db/orders.ts:7`).

Дети удаляются вместе с профилем через `onDelete: Cascade` (`prisma/schema.prisma:102`), внешние
ключи проиндексированы (`:106`). Альтернатива — удалять вручную в коде сидинга — оставила бы мусор
при любом другом пути удаления; цена каскада в том, что удаление профиля уносит его содержимое,
поэтому мутаций удаления в API нет.

В коде строка любой таблицы — это `{ id, type }` и непрозрачный набор колонок
(`src/common/contracts/types.ts:18`): сервер не перечисляет поля, их знает схема GraphQL, поэтому
DTO на каждую модель только копировали бы поля и ломались при проекции. `type` — `String`, а не
Prisma `enum`: enum попал бы в SDL через генератор типов, а значения колонки держит контракт.

## Сидинг

Сидинг читает `data/profile.yml`, проверяет его и раскладывает по таблицам; запускает его entrypoint
контейнера, поэтому база наполняется без ручных шагов. Структуру файла задаёт JSON Schema,
выпущенная из DMMF (`prisma/generators/seed-schema/seed-schema.generator.mts:51`), а
`config/seed.config.yml` добавляет только то, чего в схеме нет.

В конфиге указаны путь к файлу данных, служебные колонки (`profileId`, `order`) и натуральные ключи
(`config/seed.config.yml:34`). Остальное — свойства, вложенность, обязательность, даты — выводится
из `prisma/schema.prisma`, поэтому новый столбец не дублируется в двух местах.

Стратегия записи выводится из наличия ключа: с ключом строка пишется `upsert`, а исчезнувшие
удаляются; без ключа строки родителя удаляются и пишутся заново. Всё это одна транзакция
(`prisma/seed/data/data.writer.ts:56`), поэтому повторный `docker compose up` не добавляет дублей,
а провал на любой модели оставляет базу в прежнем состоянии.

Ошибка называет файл и путь до поля: движок сообщает место внутри документа (`profile.skills[0]`),
а `prisma/seed/main.ts` добавляет имя файла один раз (`prisma/seed/main.ts:80`).
Поэтому битый файл роняет контейнер, а не отдаёт пустой профиль: общий текст «невалидный YAML»
заставлял бы искать поле глазами.

`Prisma.dmmf` в рантайме не читается: DMMF — внутренний протокол генерации, а не публичный
контракт. Альтернатива — ручные DTO и валидаторы на каждую модель — уже расходилась с базой:
колонка доезжала до таблицы, но не до файла импорта. Цена выбранного пути — генератор и
закоммиченный артефакт, который перегенерируется вместе со схемой.

## Контракт API и генерация GraphQL

Публичный API описан одним файлом `config/api-fields.yml`: запросы верхнего уровня, скалярные поля
с описаниями и связи с указанием сущности и колонки-идентификатора. Действует инверсия по
умолчанию: чего нет в файле, того нет в API (`config/api-fields.yml:9`), поэтому новая колонка не
появляется у клиента сама.

Из контракта и `prisma/schema.prisma` выпускаются три артефакта: JSON Schema самого контракта,
классы GraphQL-типов по allowlist полей и декларации резолверов — запросы
(`src/generated/graphql/resolvers/queries.resolver.ts:23`) и вложенные поля
(`src/generated/graphql/resolvers/relations.resolver.ts:28`). Все они лежат под одним корнем
`src/generated/`, поэтому признак «сгенерировано» выражается одним путём. Поведение в них не живёт:
оно в `EntityQueries` и `EntityLoader`.

Типы генерирует `prisma-nestjs-graphql` с конфигом видимости: всё, чего нет в контракте, помечается
`@HideField()` (`src/generated/graphql/entities/profile/profile.model.ts:24`). Альтернатива —
`@Field()` на каждой колонке — публиковала бы `slug`, `profileId` и `order`; цена allowlist в том,
что новое поле API требует правки контракта, а не только схемы.

Ручные резолверы заменены генерацией: связь — это факт схемы плюс контракт, и писать её заново для
каждой сущности значит повторять одну строку и забывать её при добавлении модели
(`prisma/generators/graphql/graphql.generator.mts:48`). Цена — артефакты лежат в git, и их
актуальность проверяется отдельно.

Актуальность держит тест паритета: `tests/unit/generated/artifacts.parity.spec.ts` перегенерирует
артефакты в одноразовой копии проекта и сравнивает их с закоммиченными байт в байт. Забытая
перегенерация или ручная правка роняет `npm test`, так что дрейф — ошибка теста, а не поле в проде.

## Доступ к данным

Слои `db` и `graphql` не импортируют друг друга: единственная их общая точка — интерфейс
`IEntityQueryPort` с одним методом `find(type, query)`
(`src/common/contracts/types.ts:91`). Провайдер разрешается по токену `ENTITY_QUERY_PORT`
(`src/common/contracts/entity-query.port.ts:9`): тип стирается при компиляции, поэтому имя
провайдера задаёт значение, а `Symbol` токена не сталкивается с именами классов.

Порт связывается с реализацией в одном месте — `DbModule` (`src/db/db.module.ts:23`), и модуль
глобальный: иначе API-слою пришлось бы импортировать `src/db`. Композиционный корень
(`src/app.module.ts:21`) — единственный, кто знает оба слоя; это же правило закреплено линтером.

`prisma.*` вызывается только из `EntityRepository`: репозиторий не содержит бизнес-правил, а
`take`/`skip` уходят в SQL, поэтому клиент не читает записи, которых не просил
(`src/db/find-args.ts:34`). Один метод обслуживает все таблицы и три формы запроса: страницу,
коллекцию по родителям и список идентификаторов.

Отдельного `service` нет: правило «пустая таблица — это 404» принадлежит транспорту и живёт в
резолвере (`src/graphql/queries/entity-queries.ts:34`), а сервис только пересылал бы вызов. Маппера
тоже нет: строка уходит в GraphQL как есть. Репозиторий на сущность повторял бы один `findMany`
пять раз и рос бы с каждой таблицей.

Цена обобщения — тип сущности остаётся строкой: компилятор не проверит, что `type` существует, и
опечатка выйдет ошибкой рантайма. Ограничение закрывают контракт и генераторы: в API попадает
только то, что названо в `config/api-fields.yml`.

## Батчинг и стоимость запроса

Вложенные поля решаются батчингом: два request-scoped `DataLoader` — коллекция по родителям и
ссылка по идентификатору (`src/graphql/loaders/entity.loader.ts:43`). `Scope.REQUEST` не украшение:
кэш лоадера живёт один запрос, иначе после изменения базы клиент получал бы устаревшие строки.

Какая таблица и какая колонка участвуют в связи, лоадер не знает: он берёт это из контракта через
`referenceOf`. Альтернатива — писать `@ResolveField` с `prisma` вручную — вернула бы и колонку
`profileId`, и запрос на каждую строку; цена — новая связь объявляется в контракте, а не в
резолвере.

За один тик лоадер собирает запросы всех соседних резолверов и делает один `find` на таблицу
(`src/graphql/loaders/entity.loader.ts:103`). Альтернатива — `include` в верхнем запросе — требует
объявить связи заранее, а selection set известен только из входящего документа: `include` тянул бы
все коллекции всегда, включая те, что клиент не просил.

Число запросов не растёт с числом родителей: e2e-тест считает вызовы порта и требует ровно пять
чтений при одном профиле и те же пять при трёх (`tests/e2e/batching.e2e-spec.ts:136`). Цена —
вместо одного соединения таблиц получается несколько простых запросов; выигрыш в том, что их число
зависит от запрошенных таблиц, а не от количества строк.

Стоимость операции ограничена правилом валидации: коллекция стоит 10 единиц, скаляр 1, лимит 100
(`src/graphql/rules/constants.ts:24`). Лимит по глубине здесь бесполезен — схема плоская, три
уровня; запрос из ТЗ стоит 37, пять алиасов коллекции — 105 и отклоняются до обращения к базе.

## Docker и запуск с нуля

`Dockerfile` собран в три стадии: зависимости, сборка, минимальный runtime (`Dockerfile:6`). В
runtime попадают production-зависимости, `dist`, конфиги и данные; приложение работает от
непривилегированного `node` (`Dockerfile:74`), живость проверяет `curl` (`Dockerfile:79`).

Entrypoint готовит базу и передаёт управление приложению: `prisma migrate deploy`, затем сидинг,
затем `exec node dist/main.js` (`docker/entrypoint.sh:21`). `exec` заменяет shell процессом Node.js,
поэтому PID 1 — `tini` из `init: true`, который пересылает SIGTERM и пожинает зомби.

`migrate deploy` выбран вместо `migrate dev` потому, что второй требует shadow базы и
интерактивности — в контейнере это непригодно. Цена: схема меняется отдельным шагом разработчика, а
контейнер только применяет закоммиченные миграции.

Prisma CLI лежит в `dependencies`, а не в `devDependencies` (`Dockerfile:38`): контейнер сам
применяет миграции, значит CLI нужен в runtime. Цена — размер образа; выигрыш — `docker compose up
--build` не требует ручного шага и не зависит от подготовленной базы.

`docker-compose.yml` держит порядок запуска: healthcheck `pg_isready` и `depends_on:
service_healthy` не дают миграциям стартовать раньше базы, том `pgdata` переживает `down`, а
`init: true` даёт штатную остановку (`docker-compose.yml:30`). Приложение завершается по SIGTERM
благодаря `enableShutdownHooks()` (`src/main.ts:27`).

Проверить эндпоинт можно сразу после старта: `curl -sS http://localhost:3000/graphql -H
'Content-Type: application/json' -d '{"query":"{ profile { name } }"}'` вернёт `200` и
`{"data":{"profile":{"name":…}}}`. `Accept: text/html` к POST неприменим — 406; он нужен только
`GET /graphql`, по которому отдаётся страница Sandbox.

## Качество, тесты и границы модулей

Границы слоёв держит линтер, а не договорённость: правило `boundaries/dependencies` запрещает
`db` → `graphql`, `graphql` → `db` и `common` → оба (`eslint.config.mjs:228`). Элементы описаны
шаблонами папок, поэтому новый файл внутри слоя классифицируется автоматически, без правки правил.

Альтернатива — соглашение в документе: первый срочный импорт проходит ревью и остаётся навсегда.
Цена правила в том, что слой описывается двумя шаблонами (подпапки и корень), иначе файл в корне
остаётся неклассифицированным и проверка его пропускает.

TypeScript-проектов пять: приложение, инструменты `prisma/` на `.mts`, сидинг, тесты и библиотека
конфигов. Разделение вынужденное: у генераторов другая модель модулей и запрещён нестираемый
синтаксис, у тестов свои глобальные типы и алиасы, у сидинга собственный `outDir`. Цена —
`typecheck` гоняет четыре проекта, сидинг проверяется сборкой (`package.json:15`).

Неиспользуемый код и зависимости ищет `knip`: точки входа перечислены явно, потому что генераторы и
e2e-спеки запускаются снаружи, а не импортируются (`knip.jsonc:34`). Без этого списка knip счёл бы
рабочие файлы мусором, а вместе с ними — и нужные dev-зависимости.

Юнит-тесты проверяют то, что решается в коде: батчинг лоадера на подменённом порте
(`tests/unit/graphql/loaders/entity.loader.spec.ts`), правило стоимости на настоящем SDL,
валидаторы и генераторы; e2e идут против живой PostgreSQL — Sandbox, 404 на пустой базе,
интроспекция в production (`tests/e2e/application-surface.e2e-spec.ts:28`). Раскладка — папка на
подсистему, суффикс роли в имени файла.

## Инструменты Prisma

Инструменты лежат рядом со схемой: `prisma/generators/` выпускает артефакты из DMMF,
`prisma/scripts/` содержит хуки установки и генерации, `prisma/seed/` — движок сидинга. Провайдер
генератора — локальный Node-скрипт, а не опубликованный пакет (`prisma/schema.prisma:31`): Prisma
запускает его как команду из корня проекта.

Все они написаны на `.mts`, потому что `package.json` объявляет `type: commonjs`, а файлы запускает
голый `node` или чужой код. Расширение делает файл ESM независимо от пакета, а Node 24 исполняет
TypeScript стиранием типов — отдельная сборка для запуска не нужна, и `tsconfig.generators.json`
только проверяет типы.

Отсюда ограничение — стираемый синтаксис: `enum`, `namespace`, parameter properties и декораторы в
рантайме не существуют, поэтому `erasableSyntaxOnly` в `tsconfig.generators.json:17` делает их
ошибкой компиляции, а не падением при генерации.

Генератор и хук — разные вещи. Генератор объявлен в схеме (`provider`, `configFile`) и запускается
`prisma generate`; хук — обычный npm-lifecycle (`postinstall`) или вторая половина скрипта
(`prisma:generate`, `package.json:22`). Смешивать их нельзя: `prisma generate` вызывает и
`postinstall` самого `@prisma/client`.

Хук нужен из-за этой вложенности: `postinstall` клиента перегенерирует `src/generated/graphql/entities`
и возвращает неиспользуемые импорты, на которых `tsc` падает с `TS6133`. Корневой `postinstall`
запускает очистку ещё раз (`prisma/scripts/post-install.mts:34`) и молча выходит, если каталога
нет, — иначе `npm ci` в стадиях образа ломал бы `docker compose up --build`.

## Компромиссы и что сделал бы дальше

Мутаций и CRUD-админки нет: задание требует чтения визитки, а запись потребовала бы авторизации,
валидации входа и отдельного контракта записи. Отказ осознанный — усилия ушли в чтение, батчинг и
генерацию, то есть в то, что оценивается, а не в форму редактирования.

Авторизации нет, потому что визитка публична по смыслу: любой посетитель должен видеть профиль без
регистрации. Фронтенда тоже нет: Apollo Sandbox закрывает демонстрацию API, а свой UI дублировал бы
работу GraphQL-клиента и ничего не добавлял бы к проверке сервера.

i18n и загрузки файлов нет: контент один и на русском, а картинки и резюме в задании не заявлены.
Мультипрофильность модель допускает, но API отдаёт её только на чтение: `profiles` — страница,
`profile` — первый профиль по `createdAt`. Владения профилями и прав на них нет — без них это была
бы витрина без ответственности.

Известное ограничение транспорта: `POST /graphql` без `Content-Type: application/json` отклоняется
как CSRF — так Apollo Server 5 защищается от подделки запросов, и это штатное поведение, а не сбой.
Второе: битый `data/profile.yml` роняет entrypoint, и `restart: unless-stopped` перезапускает
контейнер по кругу; пустой профиль в ответе был бы хуже.

Часть решений принята с ценой, и она названа прямо: генерация контракта добавляет артефакты в git и
шаг перегенерации, лимит стоимости отклоняет тяжёлые запросы (пять алиасов коллекции — уже 105 при
лимите 100), allowlist не пускает новую колонку в API без правки контракта. Взамен дрейф ловят
тесты, а не внимание ревьюера.

Дальше проект расширялся бы в сторону записи: мутации и админка на тех же портах и генераторах,
затем несколько профилей с владением и правами. После этого — кэширование чтения, наблюдаемость
(метрики запросов и стоимости операций) и публикация SDL как стабильного контракта для клиентов.

## Быстрый старт

Основной путь — Docker; локальная сборка нужна только для разработки. На машине должны быть Docker
и плагин Compose, больше ничего: база поднимается сервисом `db` из `docker-compose.yml`.

```bash
docker compose up --build
```

После старта Apollo Sandbox доступен на `http://localhost:3000/graphql`, а healthcheck — на
`http://localhost:3000/health` (ответ `{"status":"ok"}`). Миграции и сидинг выполняет entrypoint,
ручных шагов нет: повторный запуск на том же томе не создаёт дублей.

Остановка — `docker compose down`; данные при этом сохраняются в томе `pgdata`. Полный сброс вместе
с данными — `docker compose down -v`, после него следующий запуск снова поднимает базу с нуля.

Локальный запуск без образа приложения: `docker compose up -d db`, затем `cp .env.example .env`,
`npm ci`, `npm run prisma:migrate:deploy` и `npm run start:dev`. Сидинг локально —
`npm run build:seed && npm run prisma:seed`. e2e-тестам нужна живая PostgreSQL:
`docker compose up -d db`, затем `npm run test:e2e` — тестовые базы готовит их globalSetup.

## Переменные окружения

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `DATABASE_URL` | строка подключения PostgreSQL для Prisma; обязательна | нет, без неё приложение не стартует |
| `PORT` | порт HTTP-сервера | `3000` |
| `NODE_ENV` | режим работы: `development`, `production`, `test` | `development` |
| `POSTGRES_USER` | пользователь базы в compose | `postgres` |
| `POSTGRES_PASSWORD` | пароль базы в compose | `postgres` |
| `POSTGRES_DB` | имя базы в compose | `it_smi` |

`.env.example` содержит три переменные приложения — `DATABASE_URL`, `PORT`, `NODE_ENV`; сам `.env` в
git не попадает. Переменные `POSTGRES_*` читает только `docker-compose.yml`, и из них же собирается
`DATABASE_URL` внутри compose. Пара `postgres`/`postgres` и опубликованный порт `5432` — только для
разработки: при развёртывании значения задаются переменными окружения, а порт базы наружу не
публикуется.

Хост в строке подключения зависит от способа запуска: локально — `localhost:5432` (порт проброшен
из контейнера `db`), внутри compose — `db:5432`, имя сервиса. Значение из `docker-compose.yml`
переопределяет строку из `.env`, поэтому один файл работает в обоих режимах.

## API

Эндпоинт один — `POST /graphql`; `GET /graphql` в браузере открывает Apollo Sandbox, он же включён и
в production вместе с интроспекцией (`src/app.module.ts:36`). HTTP-healthcheck — `GET /health`.

Запросы верхнего уровня: `profile` — первый профиль по `createdAt` (`src/db/orders.ts:7`)
или 404 на пустой базе; `profiles` — страница с `limit` (по умолчанию 10, максимум 100) и `offset`
(0); `health` — статус приложения. Типы: `Profile`, `SocialLink`, `Skill`, `Experience`, `Project`,
`Health` и enum `SocialKind`.

Запрос из задания:

```graphql
query {
  profile {
    name
    description
    skills {
      name
    }
    experience {
      company
      position
    }
    projects {
      name
    }
  }
}
```

Пример с вложенными полями и ссылками:

```graphql
query {
  profile {
    name
    links {
      label
      url
      kind
    }
    experience {
      company
      position
      startedAt
      endedAt
      finished
      achievements
    }
  }
}
```

`POST /graphql` принимает обычный JSON: достаточно `Content-Type: application/json`, других
заголовков не нужно. 400 CSRF приходит, когда `Content-Type` нет или он «простой» (`text/plain`,
`application/x-www-form-urlencoded`, `multipart/form-data`): так Apollo Server 5 отсекает запросы,
которые браузер отправил бы без preflight. Из браузера Sandbox отправляет запросы сам, поэтому
демонстрация через него в эту защиту не упирается.
